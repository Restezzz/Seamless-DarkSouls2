# Dark Souls II: SotFS — карта внутренностей для Seamless Co-op

Справочник по всему, что разобрано в игре: где что лежит, что за что отвечает,
какие байты и функции мод трогает и почему. Ведётся по ходу работы — каждая
новая находка дописывается сюда.

---

## 0. Как читать

- **Адреса — RVA**: смещение от начала `DarkSoulsII.exe` в памяти. В коде мода
  всегда `GetModuleHandle(nullptr) + RVA`.
- **Ghidra**: проект загружен с базой `0x7FF6ADA80000`, поэтому
  `адрес в Ghidra − 0x7FF6ADA80000 = RVA` (например `FUN_7ff6add21d50` → `0x2A1D50`).
- **Статусы**: ✅ в сборке и проверено в игре · 🧪 в сборке, ждёт проверки ·
  🔍 найдено, пока не используется · ❌ проверено и отвергнуто (не трогать).
- Если игра обновится, адреса съедут: сначала сверять байты в таблице патчей
  (раздел 2) — мод и сам отказывается патчить, если байты не совпали.
- **Метод, который обязателен**: полярность ветки нельзя выводить из чтения
  дизассемблера (ошибался трижды). Новый патч сначала получает переключатель,
  проверяется инверсией на живой игре и только потом идёт в сборку.

### 1.2 Сетевой корень `*(exe+0x1616CF8)`

| Смещение | Что |
|---|---|
| `+0x00` | сетевая база: `+0xA4 == 2` — залогинен на сервер; vtable `+0x78` — отправка P2P-пакета игры |
| `+0x18` | менеджер мультиплеера (тик `0x2C9540`): `+0x40` контроллер входа гостя, `+0x48..+0x50` контроллеры приёма хоста |
| `+0x20` | `+0x5B8 → +0xC` — номер текущей карты (закодирован), `+0x8` — число игроков |
| `+0x30` | NetSvr-менеджер (тик `0x291170`): `+0x50` реестр сетевых задач |

## 3. Функции игры по системам

### 3.1 Костёр и отдых

- `0x451E50` — исполнитель действий игрока: case `0xE` костёр → `0x452790` →
  `0x1CB950` (гейт, патчи выше); case `0x1B/0x1E/0x1F` подбор → `0x4528F0`;
  case `0xC` касание знака → `0x452BE0`.
- `0x17DC40` — начало действия у костра → `0x17F610` «сесть»: `0x198680` →
  установщик состояния `0x199E40(obj, 10)`, флаг события `0x19E24`, флаги PlayerCtrl.
- `0x199A70` — обновление состояния костра игрока (в состоянии 10 в коопе звал
  `0x1994E0` «встать» — выключено патчем `0x199C30`).
- `0x17ED90` — машина состояний меню костра; в `0x17F062` хвостовой `JMP` в `0x17FD70`.
- **`0x17FD70` — сброс мира при отдыхе** (без аргументов, всё из GMImp):
  - `0x417210([GMImp+0x40])` — генераторы врагов: снять врагов, сбросить 42
    области, поставить всех в очередь на появление, пауза спавна 6 кадров (`+0x331`);
  - `0x3C1B50` → `0x3C27F0(0, 0)` — объекты карты в исходное состояние;
  - `0x44F880([GMImp+0x70])` — сброс менеджера событий.
  - Мод перехватывает её и повторяет у напарника (`world_sync.cpp`, пакет `WorldReset`). ✅
- `0x17FFA0` — раздув костра (Bonfire Ascetic): интенсивность костра, `0x4170E0`
  (генераторы у этого костра), `0x3C1B40` → `0x3C27F0(1, id)`, `0x44F7F0(события, id)`.
- `0x44FE30` — запоминает последний костёр (`+0x164..+0x16C`); срабатывает при отдыхе.

### 3.2 Генераторы врагов

- **EnemyGeneratorManager** — `[GMImp+0x40]` (vtable `0x10ED520`, ctor `0x4155B0`).
  - `+0x20[42]`, `+0x170[42]` — контроллеры областей;
  - списки генераторов по состоянию: `+0x388` (3), `+0x390`, `+0x398` (5),
    `+0x3A0` (6), `+0x3B0` (8);
  - `+0x331` — пауза спавна в кадрах (после сброса 6, апдейт вычитает по 1);
  - апдейт `0x417810(mgr, &dt)` — из главного цикла (`0x1BF010`, `0x1BF200`),
    подапдейт `0x41BF70`.
- EnemyGeneratorAreaCtrl (vtable `0x10ED2E0`), EnemyGeneratorCtrl (`0x10ED338`,
  ctor `0x411A40`), EnemyGeneratorDeadCounter (`0x10C9CD8` — счётчик для лимита
  возрождений), BossEnemyGeneratorCtrl (`0x10BECD8`), условия
  `EventConditionChr_IsMaxRespawnCount` / `IsDeadOrRespawnOver`.
- **EnemyGeneratorPacketCtrl** (vtable `0x10ED530`, обработчик `0x1F6FD0`) — у игры
  есть свои P2P-пакеты про генераторы: `'N'`, `'O'` (убить запись, `0x415E70`),
  `'P'` (`0x416610`), `'Q'` (`0x416820`), `'R'` (`0x416770`). 🔍 Основа для
  будущей синхронизации состояния врагов между игроками.
- Почему был рассинхрон: враги у каждого клиента свои, их спавнят локальные
  генераторы; хост двигает только тех, чей генератор жив у обоих. Отдых сбрасывал
  генераторы только у отдохнувшего.

### 3.3 Предметы и лут

**Подбор.** `0x451E50` (действия `0x1B/0x1E/0x1F`) → `0x4528F0` — гейт по таблице
типов персонажа `0x10BFFF0` (5 байт на тип, читают ~575 мест — таблицу не трогать,
только патч `0x452916`) → `0x1E6C60(&хэндл дропа)` → `0x1E42F0(менеджер, хэндл)`:
проверка `0x1E3D80` → выдача в сумку `0x1ABA90` → снятие дропа `0x1E4590` /
частичный `0x1E1440`. Хэндл берётся из объекта-дропа `+0x28`.

**Мировой предмет** — объект карты с `MapObjItemDropComponent` (vtable `0x10C65B8`,
ctor `0x1D2CD0`, фабрики `0x3E6390`/`0x3E7110` — без проверки на фантома, объект
у гостя **есть**). Видим и подбираем только «живой» дроп в менеджере дропов
`[[GMImp+0x38]+0x1C8]` (геттер `0x1E6550`).

| Функция | Что |
|---|---|
| `0x1D2E70` | init: если дропа нет — бросить лот (`0x1E26F0` → `0x16DB10` → `0x1E2820`), создать дроп `0x1E39E0`, записать хэндл `0x1DE530` |
| `0x1E60A0` / `0x1E6410` | создать дроп по сохранённому хэндлу / снять (аргумент — ссылка на объект `0x17B2C0`) |
| `0x1D33E0` | «вкл/выкл» компонента: дроп есть, если `вкл && загружено(0x3BA430)`; на DLC-картах (`+0x58` бит 4) вместо «вкл» спрашивает модель |
| `0x1D3350` | слушатель подгрузки модели: `если +0xC == 0 → init`, дальше дроп по `0x1D32E0` |
| `0x1D34D0` | полный переброс (сброс хэндла + init), зовут `0x3BA730`, `0x3F0DA0` |
| `0x1D32E0` | модель говорит «предмет на месте»: бит 1 байта `+0xE8` у `MapModelComponent` (ctor `0x3F4410` ставит 2; сеттер `0x3F4E10`, причины — `0x3E97B0`, 3 бита в `+0x50`) |
| `0x3BA430(obj, -1)` | уровень загрузки объекта `([obj+0x90]+0x30 & 0xF) >= 3` — мультиплеер ни при чём |

**Хэндл дропа** (компонент `+0x40`, 0x14 байт): `+0` живой дроп (8 байт, «нет» =
`*(exe+0x156D290)`), `+8` лот, `+0xC` маска слотов, **когда-либо** брошенных,
`+0xE` маска того, что ещё лежит, `+0x10`/`+0x11` флаги, `+0x12` «было сохранено»,
`+0x13` вид лота. В сейв пакуется в два слова: лот `0x1DE7F0` и упакованное
`0x1DE750` (биты 0–9 = `+0xC`, 10–19 = `+0xE`, 20–21 = вид, 22/23/24 = флаги);
обратно — `0x1DE410`, для объекта — `0x1F3A10(stateMgr, obj, &лот, &упак)`.

**Два гейта мультиплеера** — поэтому гость предметов не видит (хост грузил свои
области до сессии и свои сохранил):

- `0x1E26F0` — лот из объекта карты: `если мультиплеер (0x5135F0) → пустой лот`.
  Им же пользуется init сундука `0x1CF930`.
- `0x1F31A0(stateMgr, область)` — шаг 12 загрузки области (`0x3CA8D0`): вернуть
  сохранённые состояния объектов (что уже подобрано) — **целиком пропускается** в
  мультиплеере.

**Где лежит «уже подобрано»** (оба хранилища — часть сейва, сериализатор `0x2E5A10`):

- `[mapMgr+0x200]` — полные записи трёх последних областей по 0x6008 байт
  (`0x1E7450` найти): `[0]` область, `[1]` число, с `+8` записи по 16 байт (id объекта
  в битах 2..28 последнего слова), лоты с int `0x1002`, упакованные с int `0x1402`.
- `[mapMgr+0x1F8]+0x24` — 42 компактные записи по 0xC08 байт (`0x1F4F90` найти,
  `0x1F5030` индекс по id): id с int 2 через 2, лоты с `0x182`, упакованные с `0x242`.
- id объекта: `[[obj+0x30]+0x70]`, если `[obj+0x30]+8 == 1`. Объект вида 4 —
  через `0x1729A0` → `0x449D00(·, 0)`.
- Запись из живых объектов — `0x1F22C0` (на объект `0x1F2530`), при выгрузке
  области `0x1F3A80` (из `0x3CB1A0`), при сохранении `0x2E5A10`/`0x1F2EA0` — все
  **не пишут в мультиплеере**, так что свой мир у гостя не портится.

**Решение** (`loot_sync.cpp`, ini `loot_sync`, F4 — вкл/выкл) 🧪:

1. `0x1E26F0` вызван из init предмета (`0x1D2E70`) в мультиплеере → лот строится
   как в одиночке `0x1E2B40(out, флаг+1, [row+0x24], idx?:1)`. Сундуки и дроп с
   мобов — по правилам игры.
2. После `0x1F31A0` в мультиплеере — хэндлы **только предметов** из своих записей
   (сначала полная, потом компактная); если дроп уже живой — снять, вернуть,
   пересчитать `0x1D33E0`. Двери и рычаги не трогаются.
3. Подбор в мультиплеере (`0x1E6C60`) запоминается в `ds2_coop_loot.txt` (владелец =
   имя персонажа, область, id, лот, «взято»: брошенное остаётся брошенным, лежащее
   = 0) и применяется при каждой загрузке этой области; в своём мире — один раз,
   дальше игра сама пишет его в сейв.

Копия хоста не трогается: дроп мировых предметов локальный (вид 0), между игроками
ходит только дроп с мобов (виды 2/3, `0x1E5090`).

**Сундуки** 🔍 — `MapObjTreasureBoxComponent` (vtable `0x10C62B8`, второй `0x10C6318`,
геттер у объекта `0x1E5C80`). Устроены как предмет, плюс крышка:

- хэндл дропа `+0x68` (у предмета `+0x40`), кадр крышки `+0x60` (кадр/10: 10 —
  закрыт `0x1D0860`, 50 — `0x1D06C0`, 70 — `0x1D0780`, 90/120 — открыт `0x1D0520`;
  раздаёт `0x1D0620`, зовут слушатель подгрузки `0x1CFE30` и апдейт `0x1D0070`);
- init `0x1CF930` — тот же гейт лота `0x1E26F0`; мимик (`0x3F2A10`: вид объекта 2)
  получает лот `0x2FAF468`; attach `0x1CFC70`, переброс `0x1D0020`;

### 3.6 Формат знака в сети

- `RequestCreateSign`: `online_area_id`, `cell_id`, `sign_type`, `player_struct`
  (80 байт, начинается `06 00 00 00`): `+4/+6/+8` int16 x/y/z, `+10` угол;
  значение = 32 × (мировая координата − начало карты), метры.
- Начала карт (`ds2_sign_origins.txt`): `10310000` = (−13.98, −15.02, 163.02),
  `10100000` = (207.99, 10.00, −133.02). Начало = `моя позиция − записанное / 32`.
- **Начало карты есть у самой игры** (разбор Ghidra, `E:\ghidra\out_origin\d6_decode.txt`):
  `0x2A9E70(онлайн-id, вход[4], выход[4]) → bool` пишет `вход − начало`, где начало лежит в
  `*(область+0x148)+0x2F0/0x2F4/0x2F8` (три float); область берётся из `0x3BCE00(mapMgr, сырой_id)`,
  при неудаче функция возвращает 0. С нулевым вектором отдаёт начало со знаком минус, больше ей
  ничего не нужно. На пути отправки то же вычитание делает `0x210730` (цепочка
  `0x2A2780 → 0x2A6820 → 0x210730`, 4 float ложатся в `player_struct+0x00..0x0F`); множителя 32
  в этих функциях нет, он появляется ниже, в сериализации сообщения. Поэтому измеренные руками
  начала целые: (−14,−15,163) и (208,10,−133) — расхождение 0.02 меньше шага 1/32.
  ⚠️ Четвёртая компонента (угол) в этих двух функциях обрабатывается по-разному: `0x2A9E70`
  вычитает `выход[3]`, а `0x210730` берёт глобальную постоянную — на угол правило x/y/z не
  переносить без отдельной проверки.
  **Мод не верит этому на слово:** `CheckGameOriginOnce` спрашивает начала обеих известных карт,
  сверяет с измеренными (допуск 0.1) и только при совпадении обоих пользуется функцией для
  остальных карт; результат сверки — строками `[SIGN] the game puts map … origin at …` в логе. 🧪
- Есть и **вторая, грубая система координат** (упакованная «клетка», `0x2A9F90`, начало из строки
  парам-таблицы через `0x2503A0` + бинарный поиск `0x3E8F0`) — она параметрическая и доступна для
  незагруженных карт, но совпадают ли её начала с `+0x2F0`, не проверено. Не путать с системой знака.
- `RequestGetSignList`: поле 1 = `online_area_id`.

### 3.7 Мультиплеер: вход и выход

- `0x2C9220(менеджер, причина)` — «все по домам» (зовёт событие возврата `0x190950`).
  Менеджер = сетевой корень `+0x18`.
- **NetSummonJoinMultiplayCtrl** (гость, vtable `0x10D7BD8`): состояние `+0xF8`
  (7 — в мире хоста, 8 — уход `0x2C3900`, 9, 10 — `0x2C4240`, 0xC — конец);
  слот `[A0]` `0x2C2F20` — запросить уход с причиной (только в состоянии 7),
  `[30]` — события, `[A8]` — «в мире».
- Причины ухода: 1 — успех (засчитывает кооп-успех, не использовать), **3 — обрыв
  сессии (используем)**, 2/4 — другие точки возврата (`0x2D47A0`, `0x2D4750`).
- NetSummonAcceptMultiplayCtrl (хост, vtable `0x10D7998`): слот `[E8]` пустой —
  хост этой функцией никого не выгонит; поэтому хост шлёт Disconnect, гость уходит сам.
- Уход сопровождается P2P-пакетом игры `0x11` (`0x2CE2A0`) и `RequestNotifyLeaveSession`.
- Возврат фантомов после босса: `0x191BB0` (строит `EventResult` `0x18F3A0` и
  `EventPhantomReturn` `0x18D660`), вызовы внутри выключены патчем.

### 3.8 Ввод

- Игра читает клавиатуру и мышь через **DirectInput8** (наш прокси `dinput8.dll` →
  `System32\dinput8.dll`), геймпад через `XINPUT1_3`, из USER32 импортирует
  `GetCursorPos`, `SetCursorPos`, `ShowCursor`, `SetCapture`, `GetKeyState`;
  raw input и `ClipCursor` нет.
- Мод при открытом меню: хуки `IDirectInputDevice8` `Acquire` (слот 7),
  `GetDeviceState` (9), `GetDeviceData` (10) — через vtable временного устройства,
  A и W отдельно; `XInputGetState`; `SetCursorPos`. Мышь отпускается (Unacquire)
  и захватывается обратно после закрытия. ✅
- Курсор меню — **системный** (с 2026-09-11). Курсор ImGui рисовался раз в кадр
  игры (60 FPS — «лагает»), а у друга не появлялся вовсе. Теперь хуки `ShowCursor`,
  `SetCursor`, `ClipCursor`: пока меню открыто, игра не прячет и не зажимает
  курсор; показ/возврат — из оконной процедуры (`ApplyMenuCursor`: `ShowCursor`
  действует только в потоке окна), позиция для ImGui — `GetCursorPos` каждый кадр. 🧪

- **Курсор игры** — `0xAF42B0` (менеджер ввода, из `0xAF0090`): держит копию счётчика
  `ShowCursor` в `+0x668` и флаг «нужен курсор» `+0x66C`. Нужен — зовёт `ShowCursor(TRUE)`,
  пока копия ≠ 0; не нужен — `ShowCursor(FALSE)` один раз, когда копия == 0. Там же
  `SetCursorPos` (центрирование, `+0x680 & 1`, если `+0x684 == 0`). Единственные вызовы
  `ShowCursor`/`SetCursorPos` в exe (`Refs.java`). Поэтому мод **не глотает** её вызовы, а
  возвращает ей счёт без своих прибавок (`ShowCursorDetour`: `реальный − g_showCalls`);
  иначе она читала 1, 2, 3… и звала TRUE каждый кадр (счётчик 3151, курсор в игре,
  тест 12.09).

### 3.12 Смерть, возрождение и сессия

- **Вход смерти** `0x44F6D0` (EventManager::OnChrDead) → `0x191DF0([evMgr+0x78])` ставит
  записи результата: 1 — «вы погибли», 4 — «хост погиб» (только если погиб хост
  сессии), 8/9… — по типу погибшего фантома, 0x12 — босс убит. Тип персонажа —
  `0x16F700(chr)` = `[[chr+0xB0]+0x3C]` (тип фантома; мод его обнуляет в

  и зависает камерой, так было в сборке 18:59).
- **EventResultManager** `[EventManager+0x78]` (vtable `0x10C3718`): `+0x10` EventResult,
  `+0x18` EventPhantomReturn, очереди `+0x28`/`+0x48`. EventResult (0xE8, vtable
  `0x10C3438`, создаётся на каждую загрузку `0x191BB0`): `+0xCE` «возвращаемся»,
  `+0xCF` «больше не обрабатывать» (до следующей загрузки), `+0xD8` задача, `+0xE0`
  тип фантома. Цепочка: строка параметра `тип*100 + код` (`0x44ED10`, байт 3 — причина),
  задачи из `0x156A840`, **WaitSessionJob** `0x191210` (ждёт, пока причина 2,
  категория 0 и `[[сетевой корень]+0xA4] != 0` — у хоста респаун ждёт конца сессии),
  ожидание меню, затем колбэк `0x18FFD0`: категория по таблице `0x10C0050` (20×16, байт 1)
  → **`0x190920`** (хост/соло: `0x44FDE0` — варп к последнему костру) или
  **`0x190950`** (фантом: `0x2C9220(mp, причина)` → слот A0 `0x2C2F20` контроллера входа
  → состояние 8 → варп домой; без сессии — `0x44FDE0`). Обе `(EventResult*, причина)`,
  ставят `+0xCE = 1`.
- **Из чего собирается последовательность после смерти** (12.09, разбор Ghidra, `E:\ghidra\out_msg\`).
  Она не захардкожена. `0x18F830` берёт строку параметра по ключу `тип_фантома + код*100` (общий
  табличный поиск `0x44ED10` по `[[GMImp+0x70]+0x150]+0xD8`: 16-битное число строк в `+0xA`, ключи с
  `+0x40`, шаг 8 или 0x18 по байту `+0x2D`; при промахе откат на `код*100 + 99`), копирует из строки
  **24 байта** и отдаёт их в `0x18F9C0`, а тот строит цепочку задач. Классы назвали себя сами —
  конструкторы пишут свои vftable:
  - `EventResultJob::WaitJob` — `0x190FA0`, создаётся **только при байте 3 == 1**; длительность берётся
    из параметра типа фантома: `[0x16F540(тип)+0x28]`, где `0x16F540` — поиск по `[GMImp+0x18]`.
  - `EventResultJob::WaitSessionJob` — `0x191030` → `0x190C90`, из типа фантома и байта 3; её апдейт и
    есть `0x191210` из абзаца выше.
  - `EventResultJob::ChargeVowContributeJob` — `0x190DF0`, из байта 2 (очки ковенанта).
  - `FeFunctorJob<JOB_MEMBER_FUNCTOR_ARG1<EventResult,NetMultiPlayResult,void>>` — `0x18F1A0`, из байта 3
    и адреса `0x18FFD0`. **`0x18FFD0` — метка внутри функции, а не функция**, поэтому по ней и не
    получалось взять дамп; это та самая «категория → `0x190920`/`0x190950`».
  - `EventResultJob::WaitFeEndJob` — `0x190010` → `0x190F20`, из байта 0 (ждёт конца интерфейса).
  - `EventResultJob::Remunerate` — `0x18FF20` → `0x190EA0` → `0x190C10`: **награда, а не текст**. Берёт
    dword `+8` либо `+0xC` (выбор по `0x1D12150`), «вид» 1 или 2 и флаг `+0x10`.
  - `FeFunctorJob<JOB_MEMBER_FUNCTOR_ARG1<EventResult,EventResult::MessageInfo,void>>` — `0x190160` →
    `0x18EEE0`, колбэк `0x1900E0`. **Это и есть баннер.** Создаётся **только когда байт 1 != 0**; байт 1
    выбирает способ показа, dword `+4` — id текста: 1 → `0x190A80` → `0x2D6BF0(id)` (просто текст),
    2 → `0x190AE0`/`0x190AF0` → `0x2D6C50`/`0x2D6D30(id, имя)`, 3 → `0x190A90` → то же, имя игрока берут
    через `0x1F93280` / `0x1F9B3C0(…, 0x7F00)`. В пару к нему идёт `WaitJob` с длительностью из глобали
    `exe+0xB4122C`.

  Байт 3 («причина») заодно ставит `+0xCE = 1`, поэтому **обнулять его ради баннера нельзя** — вместе с
  сообщением уедет и возврат домой. А **байт 1 читается ровно в одном месте** — в `CONCAT44(dword+4,
  байт1)` для `0x190160`, — поэтому глушить баннер надо именно им, и ничего кроме сообщения при этом не
  теряется: ни возврат, ни награда. Так и будет сделано: хук `ResultSeqDetour` на `0x18F9C0` копирует
  строку, обнуляет байт 1 и отдаёт игре копию — но только когда мод собирается **оставить гостя в мире
  хоста** (бой с боссом, хост жив), потому что в остальных случаях надпись правдива. Баннер «вы побеждены,
  возвращаемся в ваш мир» гость видел именно в этом случае, и он врал (жалоба 12.09). Проба в том же хуке
  печатает код, тип фантома, длительность ожидания и все 24 байта строки на каждой смерти — хоста, гостя и
  одиночной, — так что состав строки и полярность проверяются в игре, а не по декомпиляции. 🧪

### 3.17 Почему у гостя нет NPC (12.09, разбор Ghidra, `E:\ghidra\out_npc\`)

- **Подсказка и само появление NPC — две разные задачи**, поэтому правка §3.14 ничего и не дала.
  Поправка к §3.14: `0x453760` не отказывает всем id 1–15. Отсеиваются только id 18–19
  (`0x16F7B0`: `(byte)(id − 0x12) < 2`), а id 1–17 идут в таблицу переходов `0x4539A8`, где нужен
  конкретный бит маски прав подсказки `ctrl+0xAA..0xAC`: id 1,3 → `[0]&2`; 2,4 → `[0]&4`;
  5 → `[0]&0x10`; 6 → `[0]&0x20`; 7–10,15 → `[0]&0x40`; 11 → `[0]&0x80`; 12 → `[1]&1`;
  13 → `[0]&8`; 14 → `[1]&2`. При скриптовой маске `01 FC 0F` проходит только id 14, а у гостя
  id 1 (лог `[TRAVEL] local phantom id 1`) — отказ настоящий, но он вторичен. Классификаторы:
  `0x16F800` (id 1–17), `0x2D8670` (id 0–5), `0x4516C0` — битовая маска типа персонажа
  (бит 0 — это `[GMImp+0xD0]`, бит 3 — владелец мира, сетевой id `0x7F00`).
- **NPC у гостя вообще нет в мире**, поэтому подсказка и не создаётся (за всю сессию ни одной
  строки `[TALK]`). Два кандидата, оба в системе генераторов:
  1. **`0x40ECF0` (`EnemyGeneratorAreaCtrl::Update`).** `R14` заводится в 1 (`0x40ED7F`), и
     `CMOVNZ` (`0x40EDA1`) обнуляет его, если сессия есть и `0x5135F0()` («мир загружен
     МП-варпом») вернула не ноль. На `0x40EE7C` — `TEST R14B,R14B; JZ 0x40EF2E`: у гостя весь
     блок завершения появления (`0x412BD0`, `0x40F9C0`) пропускается целиком. Вызов предиката —
     `exe+0x40ED8E`, адрес возврата **`exe+0x40ED93`**.
  2. **Отсев по групповой маске.** `0x419D50` → `0x415D50`/`0x40F300` → `0x415E70` → `0x419460`
     → `0x40FDB0(status, 1)` снимает персонажа с карты; маску строит `0x4122D0`, проверяет
     `0x41EEE0` (ИЛИ области игрока с областями до 5 участников сессии, у каждого
     `[area+0xA2] == 2`). Возвращаемое значение `0x41EEE0` декомпилятор потерял — читать живьём.
- «Прозрачность» — скорее всего не тонировка: кода, красящего персонажа по роли или id фантома,
  нет (поиск по именам пуст, отдельного класса NPC в игре нет, NPC — обычные персонажи на
  EzState). Похоже на незавершённое появление: состояние `EnemyGeneratorChrStatus+0x76` (2 бита),
  счётчик `+0x6C`, порог `[+0x58]+0x44`.
- **Проверка инверсией (в сборке):** ответ «нет» на `0x5135F0` только для возврата `0x40ED93` и
  только когда гость уже в мире хоста (состояние 7) — тем же способом, что для сундуков
  (`MpActiveHook`, player_sync.cpp), ini `npc_spawn`, клавиша Delete. Прологи `0x40F300`
  (`48 89 5C 24 18`) и `0x41EEE0` (`40 55` + `48 8B EC`) для хука пригодны; у `0x415D50` в первых
  5 байтах короткий переход — не трогать. 🧪
- Отвергнуто с доказательствами: `0x25EA40` (роль сессии) в спавне и отрисовке не участвует;
  `0x46ED10`, `0x46F2C0`, `0x46EDD0` читают `[GMImp+0xD0]`, то есть скрипты NPC гостя видят;
  `0x410020` гейтит регистрацию дропа (`0x1E60A0`/`0x1E6410`), а не видимость; `0x419AF0` — частный
  случай карты m20_21_00_00 с флагом `0xD2C3141`; `0x3BCD90` — просто `[[mapMgr+8]+0x20]`, позиция
  хоста область генераторов не выбирает.

### 3.18 Список костров для перемещения (12.09, разбор Ghidra, `E:\ghidra\out_travel\`)

- **Где данные.** Менеджер костров = `*(*(exe+0x16148F0)+0x70) + 0x58`. Записи по 0x18 байт в
  `+0x20`, их число в `+0x28`, отсортированы по u16 id костра в `+0x00`. В записи **две**
  байтовые доступности: `+0x02` — свой набор (из сейва), `+0x03` — набор, приходящий по сессии;
  в обоих бит 0 = доступен, биты 1–7 = уровень раздува. Какой из них читает список, решает int
  «вид» в `+0x44` (0 → `+0x02`, 1 → `+0x03`). `0x17E6F0(id)` = `*(u8*)(зап + [мгр+0x44] + 2) & 1`;
  `0x17E390` так же считает доступные; `0x17E320` ставит бит 0; раздув `0x17FFA0` пишет
  `уровень*2 | (b&1)`; массив строит `0x17EC50` из парам-таблицы; сохранение и загрузка
  `0x17E540`/`0x17EB10` (блоб `+0x1598` id, `+0x1798` бит, `+0x1898` уровень, `+0x1998` маска,
  максимум 0x100) — **и то и другое только по байту `+0x02`**. Запись `+0x08` — строка
  `MapObjectBonfireParam` (`**(зап+8)` = сырой id карты), `+0x10` — битовая маска карт.
- **Вид переключает `0x17E890`** (единственный вызов — `0x44F316`): без сессии пишет 0, иначе
  `(0x5135F0() != 0)`, и попутно обнуляет набор сессии у всех записей. То есть по коду гость
  должен читать `+0x03`, а полностью его никто не заполняет.
- **Передача костров хоста в игре уже есть.** `0x17E910` пакует записи по 8 байт
  `{u16 id, u8 уровень, u8 горит}` **из байта `+0x02`**, но только для одной карты
  (`**(зап+8) == 0x3BF980(карта)`) и с ограничением из аргумента вызывающего — на `0x2B6A1A`
  это **16**. Применяет `0x17EA40`, и она пишет **только байт `+0x03`** (вызовы `0x2B9BD8`,
  `0x2C30A8`).
- **Что нужно моду:** заполнить байт `+0x03` у всех записей набором хоста — напрямую или тем же
  `0x17EA40` с массивом любой длины (ограничение 16 — это аргумент вызывающего, а не функции).
  **Байт `+0x03` не сохраняется**, поэтому сейв гостя испортить нельзя. Сначала замерить в игре
  `+0x44` и оба байта: если вид окажется 0, объяснение другое. 🧪
- **Само перемещение гостя, по коду, рвёт сессию, а не переносит.** `0x1C2A80` (RequestWarp)
  требует `[GM+0x24AC] == 0x1E` и `([GM+0x24B1] & 2) == 0`; вид 2 (перемещение по костру) всегда
  опрашивает гейт `0x248940` = `(**([GM+0xD0]+0x1B0))() != 0` (что за виртуальный метод в слоте
  `0x1B0` — не выяснено). Маршрутизация по типу персонажа `0x18FFD0` (таблица `exe+0x10C0050`,
  20 строк по 16 байт; байт+1 равен 0 только у строк 0, 18, 19) для строк 1–17 ведёт в
  `0x190950`, а та при живой сессии зовёт `0x2C9220` («все по домам») **и возвращается без
  варпа**. Значит «показать костры хоста» и «дать гостю ими воспользоваться» — две разные задачи;
  вторая требует замеров гейта и ветки. 🔍

- **Список костров — замер сошёлся с §3.18.** Хост: `view 0 (reads +0x02, my own) … lit in my own
  set 5`. Гость в мире хоста: `view 1 (reads +0x03, the session's) … in the session set 2`, и
  различаются ровно костры текущей карты (10655, 10670 — набор сессии 0x01; 2650, 4650, 31655 —
  только свой набор). То есть игра действительно отдаёт одну карту и не больше 16. Мод теперь
  шлёт весь набор пакетом `BonfireList 0x3A` и пишет его в байт `+0x03` (death_sync.cpp). 🧪
- **Завершение появления персонажей — не причина пропавших NPC.** `npc_spawn` работал, счётчик в
  логе дошёл до 24 000 вызовов, NPC не изменились; снятий с карты (`0x40F300`) — ни одного. Значит
  персонажей не создают вовсе, а не убирают и не «недопоказывают». `npc_spawn` переведён в выкл.
- **Вылет (исключение 0xC0000005, чтение по 0x0).** `#00 exe+0x18B10E` — это `CALL qword ptr [RAX]`,
  где `RAX = [RSI]`, `RSI = [RDI+0x20]`: у под-объекта нулевой указатель на таблицу методов, то
  есть он уже разрушен. `#01 exe+0x4534A6` — внутри функции `0x453480`, которая ставит vtable в
  `[RCX]` и зовёт `0x18B0D0` (та самая очистка, где `[RDI+0x20]` затем обнуляется) — **путь
  деструктора объекта подсказки** из кластера `0x4534xx` (EventKeyGuideCtrl, §3.14, §3.17).
  Единственное новое в этом кластере — наш ответ «можно» в `0x453760`: подсказка регистрируется на
  персонажа, которому не предназначалась, и её учёт (`ctrl+0xA0`, регистрация на входе и снятие на
  выходе) расходится. Причинность не доказана, поэтому `npc_talk` по умолчанию выключен, а не удалён.
  Дамп: `Game\ds2_seamless_crash_20260912_070008.dmp`, разбор — `E:\ghidra\out_crash\`.

### 3.20 Что нашлось у сообщества (12.09, поиск по подсказке пользователя)

Источники: таблица Cheat Engine **Bob Edition** для SotFS (скрипты лежат в репозитории
`boblord14/Dark-Souls-2-SotFS-CT-Bob-Edition` разобранными текстовыми `.cea`), **DS2S-META**
(`Nordgaren/DS2S-META`, `DS2SHook.cs`, `DS2SOffsets.cs`, `Resources/Systems/*.txt`) и **Paramdex**
(`soulsmods/Paramdex/DS2S`). Всё — SotFS x64.

- **Сеттер флага события у сообщества: `0x4750B0`.** Скрипт зовёт его с
  `this = [[GameManagerImp]+0x70]+0x20`, id флага в `EDX`, значение в `R8D`. У нас записан **другой**
  сеттер — `0x474A60`. Цепочка `+0x70 → +0x20` подтверждается независимо: в DS2S-META те же
  `EventManagerOffset = 0x70` и `BonfireLevelsOffset2 = 0x20`. Разбор всех трёх функций
  (`E:\ghidra\out_flags\flag_setters.txt`) даёт полную картину:
  - **`0x4750B0(this, id, значение)` — чистая запись флага, без единой проверки мультиплеера.**
    Хэш-таблица на 31 ячейку в `this+0x20`: группа = `id / 10000` (сверяется с `узел+0xC`), цепочка
    через `узел[2]`, размер группы в `узел+8`, сами байты в `*узел`; байт = `(id % 10000) >> 3`,
    бит = `1 << (7 − (id % 10000 & 7))` — **старшим битом вперёд**. Возвращает «значение
    изменилось», и при изменении зовёт `0x184FF0(this+0x10, id, значение)` — рассылку слушателям.
    Этой же раскладкой флаг можно и **читать**. Вызыватели: `0x474A60`, `0x4747C0`, `0x25CE10`.
  - **`0x474A60` — та же запись, но с гейтом и сетью:** `если (сессия && 0x5135F0() && !0x25CDB0(id))
    — выход`; затем `0x4750B0`, и если значение изменилось — `0x51E6B0(0x513230(), id, значение)`,
    то есть отправка флага в сессию.
  - **`0x25CDB0(id)` — узкий запрет, а не «гостю нельзя».** Отказ (0) только когда
    `id < 1 000 000` **и** `(id / 10000) % 100 > 2`. Значит **гостю разрешены** флаги костров
    (1002000–4003099), флаги дверей и туманов (наши `110000081`, `131000086`) и состояния NPC
    3500–3999; закрыта примерно полоса 30000–999999. **Это поправка к §3.4:** утверждение
    «сеттер отбрасывает записи гостя» неверно.

  **Что из этого следует:** прогресс хоста — зажжённые костры, открытые туманы, убитые боссы — можно
  отдавать гостю штатным `0x474A60`, и он сам отправит флаг в сессию. Но это запись в **сейв** гостя,
  поэтому только отдельной настройкой и с честным предупреждением, никогда молча. 🧪
- **Костры: независимое подтверждение нашего разбора §3.18.** DS2S-META «unlock all bonfires» идёт по
  цепочке `Base → +0x70 → +0x58 → +0x20` и пишет байт по смещению `номер × 0x18 + 2`
  (`FireKeepersDwelling 0x2`, `TheFarFire 0x1A`, `CardinalTower 0x32`, … `GrandCathedral 0x6F2`),
  где 0 = не открыт, 1 = открыт. Это ровно наш байт записи `+0x02`, то есть **они пишут «свой» набор,
  а мод пишет «сессионный» `+0x03`**. Их список id совпадает с тем, что видел наш пробник:
  2650 Fire Keepers' Dwelling, 4650 The Far Fire, 10655 Cardinal Tower. Значит структура прочитана
  верно. `BonfireHubs.txt` даёт группировку «хаб → костры», то есть форму самого меню перемещения.
- **Перемещение:** DS2S-META зовёт `SetWarpTargetFunc` + `WarpFunc`, находя их по AOB
  (`48 89 5C 24 08 48 89 74 24 20 57 48 83 EC 60 0F B7 FA` и
  `40 53 48 83 EC 60 8B 02 48 8B D9 89 01 8B 42 04`), id костра — из `Bonfires.txt`. Сам инструмент
  **запрещает** варп в мультиплеере по своему условию `ConnectionType > 1` (`Connection+0x8`,
  `ConnectionOffset 0x38`) — это его собственный отказ, не игры.
- **Параметры, которые стоит помнить:** `MAP_OBJECT_BONFIRE_PARAM` содержит `Bonfire Lit Flag ID`,
  `Area ID` и `Fog Door ID` (ссылка в `MAP_OBJECT_WHITE_DOOR_PARAM`) — то есть костёр можно зажечь
  флагом, а не байтом. Список имён флагов: `Paramdex/DS2S/Names/EventFlagListParam.txt`, 442 строки,
  id 3500–10006300; блоки: 3500–3999 состояние NPC (3750 магазин доспехов, 3760 материалов,
  3770 чародейства, 3780 кузнец, 3999 «полная враждебность»), 1002000–4003099 костры
  (【Regeneration Spark】), 10001150–10001153 боссы второго прохождения. ⚠️ Формулы «id карты → id
  флага» нет: строка `1030000` подписана как Heide, хотя Heide — `m10_31`. Проверять по месту.
- **NPC: у сообщества пусто.** Ни скрипта, ни мода, возвращающего гостю NPC, не нашлось. Зацепки:
  прозрачность настраивается таблицей `CHR_PHANTOM_PARAM` (пять наборов RGBA плюс `Ghost A1`,
  `Ghost A2`), и её строки — не только про игроков: «Usually Phantom», «Bonfire Phantom»,
  «Tomb Phantom», «Dragon Spirit Phantom», «Abyss Phantom». Имена типов фантома
  (`ChrNetworkPhantomParam`): 0 хост, 1 белый фантом, 2 тень, 3 sunbro, 5/6 синий, 7/8 красный,
  9/10 BoB, 11 Dragon Spirit, 14 Abyssal Spirit, 16/17 арена, **18/19 UNKNOWN** — последние DS2S-META
  трактует как состояние «без столкновений». Наши офсеты подтверждены со стороны: `PlayerCtrl+0xB0`
  → `ChrNetworkPhantomId 0x3C`, `TeamType 0x3D`, `CharType 0x48`. Состояние NPC задаётся ESD через
  `GENERATOR_PARAM` (`ApperanceEventID`, `ActivationEventID1/2`, `HostileEventID1/2`, `DeathEventID`)
  и `GENERATOR_REGIST_PARAM` (`SpawnState`, `EnemyParamID`, `DrawGroup`) — **поля про мультиплеер там
  нет ни одного**. По вики (слабое подтверждение, страницы про DS1) невидимость NPC у фантома —
  задуманное поведение: гостю их рисуют призраками, чтобы он не портил мир хоста. 🔍
- **Мод Yui существует** (`yuiamoroll/DarkSouls2SeamlessCoopRelease`, только SotFS): сессия живёт
  через смерти, боссов и телепорты, нет границ и таймеров, опционально полная синхронизация

### 3.21 Общий прогресс через флаги (12.09) — почему функция молчала

Синхронизация флагов была в моде с самого начала и **работала вхолостую**: дифф считался, в лог
писался, а до отправки дело не доходило. Убивали её две её же защиты.

1. **Пустая группа останавливала весь пасс.** Таблица флагов пересобирается при переходе между
   мирами, и поймать её можно на нуле. Проверка «группа была заполнена, а теперь пуста» делала
   `return` **до** замены базовой линии, поэтому после первого же раза сравнивать было больше не с
   чем — навсегда. В сессии 12.09 группа 20 читалась пустой на каждом пасу: 994 такие строки у
   гостя, 541 у хоста. Теперь из диффа выпадает **только** эта группа, с сохранением её прежних
   байтов, а остальные сравниваются как обычно.
2. **Предел «не больше 8 изменений за пасс»** — один костёр, один туман или загрузка области двигают
   больше, и каждый такой пасс выбрасывался целиком как «пересборка таблицы». Высокий предел
   безопасен из-за того, что именно отправляется: только биты, которые **в нашей же таблице стоят
   единицей**, и только в направлении 0→1. Худшее, что сделает пасс, похожий на пересборку, —
   расскажет второму игроку о прогрессе, который у нас действительно есть. Осталось 256, и только
   как защита от лавины пакетов.

**Дифф рассказывает лишь о том, что менялось при обоих.** Гость, зашедший после того как хост зажёг
пять костров и открыл три тумана, не узнаёт ни об одном — ровно то, что видели в тесте 12.09.
Отсюда пакет `FlagBulk` (0x3B): хост один раз за подключение отдаёт свои группы целиком (по замеру
5 групп, 2575 байт → 5 пакетов по 669 байт; приёмный буфер 8192), гость выставляет у себя только
единицы. Только от хоста к гостю: это выгрузка целого сейва, и просили именно «отдать мир хоста».

**Запись — всегда в игровом потоке.** Пришедшие флаги кладутся в очередь, а пишет их `FlagSyncTick`:
вызов функций игры из сетевого потока уже однажды ронял игру на повторе отдыха у костра. За пасс
пишется не больше 400 флагов — сеттер `0x4750B0` уведомляет слушателей, и мир реагирует на месте
(туманы, двери, костры).

Остальное, что делает запись безопасной:

- Флаг из группы, которой в этом сейве нет (или за пределами её размера), отбрасывается: у сеттера
  нет такого бакета. У обоих игроков группы совпали — 5 групп, 2575 байт.
- Записанный флаг сразу вносится в базовую линию, иначе дифф отправит его обратно и два клиента
  будут гонять его вечно.
- Снимать умеем только вверх: `0→1` шлётся и применяется, `1→0` не шлётся и не принимается никогда.
  Ложная единица стоит лишнюю открытую дверь, ложный ноль — потерянный прогресс в чужом сейве.
- Вся таблица уходит в `ds2_flags_backup.bin` (группа u32, размер u32, байты) при первом снятии
  базовой линии — до того как применится хоть что-нибудь.
- ini `flag_sync = on | off`, по умолчанию **on** с 0.1.3. Слово `log` (старое значение по
  умолчанию, «только смотреть») теперь означает `on`: иначе оба игрока правили бы ini руками ради
  функции, которую сами и просили. 🧪

### 3.22 Почему Маджула не лечилась три релиза (12.09, логи обеих сторон)

- **Проверка «верить ли началу карты от игры» требовала обе карты сразу.** Список измеренных руками:
  `10310000`, затем `10100000`. Запрос `0x2A9E70` отвечает только для карты, чьи данные загружены;
  первая почти никогда не загружена рядом со второй, и цикл выходил по `return` — доверие навсегда
  оставалось «не проверено», ответ игры **не использовался ни разу**, всегда побеждало значение с
  диска. В логах обеих сторон за 12.09 нет ни одной строки из этой проверки — она и есть
  доказательство. Теперь карты проверяются по одной (`continue` вместо `return`), доверие ставится по
  тем, что ответили, а «не ответила ни одна» печатается один раз. **И в тесте 12.09, 06:51:14 игра не
  ответила ни про одну из них — включая карту, в которой игрок стоял:** `the game cannot resolve either
  of the maps measured by hand yet`. Значит `0x2A9E70` требует чего-то ещё (другого аргумента, загруженного
  менеджера карт, иного момента) либо `*(area+0x148)+0x2F0` — не то место. Проверка теперь хотя бы честно
  об этом говорит вместо молчания, но источником числа игра пока так и не стала. 🔍
- **Откуда взялось `(10.53, 5.92, -16.25)`.** Лог хоста 08:21:13: `player x=10.53 y=5.92 z=-16.25`, и
  сразу `origin learned from my own sign: (0.03, 0.02, -0.00)` — то есть настоящее начало Маджулы
  ≈ ноль, а отравленное значение было просто позицией стоявшего там игрока. Из файла хоста я его
  убрал, но знак ставит **гость**, а `NoteRemoteMapOrigin` отказывался перезаписывать уже имеющуюся
  запись («своё измеренное не трогаем»): хост измерял правильно и отправлял каждые 10 секунд, гость
  выбрасывал. Теперь своё выигрывает только если получено **в этом запуске** — от игры или своим
  знаком в этой же карте (`g_originMeasuredHere`); прочитанное с диска уступает измеренному партнёром.
- **`GetLocalMapOrigin` смотрел только в таблицу с диска**, а им пользуются и рассылка начала карты, и
  пробный знак. Теперь идёт через `LookupMapOrigin`, то есть сначала спрашивает игру. Побочно это
  убирает **пробный знак хоста**: он ставился ровно по причине «начала нет» — это и был знак призыва,
  появившийся под хостом в Маджуле (`nobody else in the session — sign stays where I placed it`).
- Загруженные начала печатаются со значениями, а не только числом штук.
- **Что на самом деле починило Маджулу (тест 12.09, 06:52, лог гостя).** Не ответ игры, а снятый запрет на
  перезапись: 06:52:36 знак **дождался** (`map 10040000 has no origin here, so a sign cannot be aimed into
  it -- the sign waits`), 06:52:40 пришло измеренное хостом `(0.02, 0.01, -0.01)` и было **принято**, там же
  знак прицелен, 06:52:58 гость появился в `(4.34, 5.49, -17.75)` при позиции хоста `(4.38, 5.49, -17.77)` —
  расхождение 4 см. Призыв в Маджулу работает. ✅ Отсюда же следствие: пробный знак хоста остаётся
  **единственным** способом получить начало новой карты, пока игра не отвечает, — он снова появится в карте,
  которую никто не измерял, и это плата за работающий призыв, а не баг.
- **Флаги дошли до сейва гостя:** его `ds2_flags_backup.bin` до и после — группа 10 12 → 13 единиц,
  группа 20 0 → 4. Из этого же вышло про NPC: те, кого гость **вообще не видел**, стали прозрачными. Значит
  их не «не создают» — им не хватало флагов появления, и остаётся ровно две задачи: призрачный вид и отказ
  во взаимодействии (§3.17). ✅🔍
- **Костры: сессионного байта недостаточно.** Замер: у хоста 5 зажжённых (2650, 4650, 10655, 10670,
  31655), гостю ушли все 5, у записи 10670 сессионный байт `+0x03` = `0x01`, вид списка 1 (читает
  `+0x03`) — и костра в меню перемещения всё равно нет. Значит меню читает не только этот байт; что
  именно ещё — не разобрано. Пока при включённом общем прогрессе костёр партнёра зажигается и в
  **своём** байте `+0x02` (только бит 0, уровень разжигания не трогаем), то есть отдаётся насовсем. 🧪
- **Выход из мира после призыва:** `join controller asked to leave: reason 3, state 7` (лог гостя
  06:22:53) — игра сама завершила сессию через ~40 с после появления в Маджуле, перед этим гость
  получил урон (HP 826 из 867). Что означает `reason 3` — неизвестно; это следующая зацепка, если
  после исправления начала карты выход повторится. 🔍

  `m_peersMutex`; тот же компьютер под новым id вытесняет свою старую запись молча
  (`RemovePlayer(id, true)`).

| Тип | Пакет | Смысл |
|---|---|---|
| `0x01` | Handshake | вход в лобби по паролю |
| `0x02` | Disconnect | до рукопожатия — отказ, после — «хост закрыл лобби» (гость уходит домой) |
| `0x03` | Heartbeat | |
| `0x20` | PlayerPosition | позиция + `onlineAreaId` |
| `0x22`–`0x24` | PlayerState / Death / Respawn | Death/Respawn без полей (кто — по отправителю). Шлёт только `NotifyPlayerDeath/Respawn` для **своего** игрока; приём — `SetPlayerAlive`, без пересылки (раньше приём звал `Notify*`, и пакет гонял бы между клиентами бесконечно — как когда-то флаги) |
| `0x34` | EventFlag | синхронизация флагов |
| `0x35` | SignPlaced | «я поставил знак» — у хоста срочный опрос и автопризыв |
| `0x36` | WorldReset | «я отдохнул» — у получателя повтор сброса мира ✅ |
| `0x37` | BossState | бой с боссом у хоста: `active`, `phase` (§3.12) |
| `0x38` | MapOriginInfo | начало карты для координат знака: `area`, `x/y/z` (§3.6) |
| `0x39` | BossDoorCrossed | «я прошёл туман с этим флагом» — копия двери у гостя этого не видит (§3.14) |
| `0x3A` | BonfireList | все свои костры: `count` + записи `{id u16, флаги u8}` (§3.18) |
| `0x3B` | FlagBulk | уже сделанное: `group`, `bytes`, до 640 байт битов. Хост → гость, один раз за подключение (§3.21) |

## 6. Сервер (ds3os, `Server_upstream`)

- `DS2_SignManager.cpp`, `Handle_RequestGetSignList`: проход без областей поиска,

- Ключ клиента `ds2_server_public.key` должен совпадать с

- `Handle_RequestRejectSign` (2026-09-11): знак ищется и по id во всех
  областях (он перемаркирован в область хоста, а отказывающий сообщает свою),

  оставались без ответа → «Потеряно соединение с сервером игры» до перезахода

- Сборка сервера: запущенный `Server.exe` держит открытым `Server.pdb` из папки

  Выложить: запущенный exe можно переименовать (`Server.prev.exe`), новый —
  на его место; вступает в силу после `StartServerUpstream.bat`.
- **12.09: исправление `Handle_RequestRejectSign` не срабатывало вовсе** — до него
  дело не доходило. Клиент прислал `RequestRejectSign` без части из пяти

  смог разобрать сообщение (`ds2srv_new_err.txt`: «missing required fields») и

  это и было «Потеряно соединение». Теперь `Frpg2ReliableUdpMessageStream.cpp`:
  если `ParseFromArray` не прошёл, пробуется `ParsePartialFromArray` (недостающие
  поля — по умолчанию, в лог предупреждение). Запущенный сервер держит и
  `Server_seamless.pdb` — копия проекта для этой сборки `Server_s2.vcxproj`

- Лог сервера: `%TEMP%\ds2srv_new_out.txt` (Log/Warning), `ds2srv_new_err.txt`
  (ошибки protobuf) — пишутся батником `StartServerUpstream.bat`.
- **Игрок после вылета игры** (12.09, 01:24–01:25): его старое соединение висит в
  `Clients`, пока ретрансмиты не сдадутся (~1 мин: «Attempted retransmission …
  assuming connection has died»), а `GameService::FindClientByPlayerId` отдавал
  **первое** совпадение — мёртвое. Призыв знака перезашедшего игрока
  (`PushRequestSummonSign`) уходил в мёртвое соединение, у него «только
  подключение». Теперь `FindClientByPlayerId`/`FindClientBySteamId` ищут с конца —
  самое новое соединение (сборка `Server_s3.vcxproj`, PDB `Server_s3.pdb`).
  И сразу при повторном входе (`DS2_BootManager::Handle_RequestWaitForUserLogin`,
  после `SetPlayerId`) все прежние соединения того же игрока получают
  `DisconnectTime = GetSeconds()` и выбывают на следующем `Poll` — вместе с ними
  `OnLostPlayer` снимает их знаки (иначе мёртвый знак 1000 продолжал предлагаться
  хосту рядом с новым 1001). Цикл с `FindClientBySteamId` в том же обработчике —
  только `_DEBUG`, порядок поиска на вход не влияет.
  Если хост всё же призывает старый знак (его игра держит старый id: мод хоста
  блокирует `PushRequestRemoveSign`, а автопризыв через 6 с после пинга берёт
  «самый новый известный» знак — им может оказаться старый),
  `Handle_RequestSummonSign` не отказывает, а призывает текущий знак того же
  игрока (`sign_info.player_id`, наибольший `SignId`, не занятый призывом).
  Отказ хосту был бы всё равно заблокирован его модом (`RejectSign`), и игра
  хоста ждала бы призыва, который не придёт.
- **Лобби мода (§5)**: в режиме seamless пиры не выбывали по тайм-ауту вовсе, и
  вылетевший игрок висел в лобби вечно (два «ee»). Теперь: рукопожатие с того же
  адреса под новым id вытесняет старую запись (`HandleHandshakePacket`), а в
  seamless — тайм-аут 3 мин тишины (обычный — 60 с). Вытеснение —
  `RemovePlayer(id, true)`: без тостов «вышел» / «все вышли» перед «вошёл».
  Регистрация пира в `HandleHandshakePacket` (и у клиента — правка записи хоста)
  теперь под `m_peersMutex`: это поток сети, а игровой поток шлёт по тому же
  списку, и `push_back` без замка мог переложить вектор под читателем.
  `CheckTimeouts` берёт замок сам и зовёт `SessionManager::RemovePlayer` уже без
  него (как и все прочие переходы PeerManager → SessionManager).
- Вылет гостя при загрузке мира хоста (12.09, 01:24, ee; дампа нет): единственное
  новое, что действует на мир при загрузке, — локальная «раскладка» сундуков;
  теперь она только после состояния 7 контроллера входа. Для точной причины нужен
  дамп друга (`%LOCALAPPDATA%\CrashDumps`).
- **Журнал вылетов мода** (`src/utils/crash_log.cpp`, с 12.09): фильтр
  необработанных исключений (ставится в начале потока инициализации; после
  `Initialize` MinHook-перехват `kernelbase!SetUnhandledExceptionFilter` держит
  его первым, чужие фильтры встают в цепочку за ним). Работу делает заранее
  созданный поток: в конце `ds2_seamless_coop.log` — строки `[CRASH]`: код
  исключения, `модуль+смещение`, для AV — чтение/запись и адрес, регистры, стек
  по таблицам раскрутки (`RtlVirtualUnwind`) и сырой просмотр стека
  (`exe+RVA`/`mod+RVA`); рядом `ds2_seamless_crash_ГГГГММДД_ччммсс.dmp`
  (MiniDumpWithIndirectlyReferencedMemory). RVA `exe+` — прямо в Ghidra
  (база 0x7FF6ADA80000); для `mod+`/`dinput8.dll+` — PDB этой сборки из
  `symbols/<md5>/` (Release теперь собирается с /Zi /DEBUG /OPT:REF /OPT:ICF).
- **Сборка мода — только `--clean-first`**: каталоги сборки лежат в %TEMP%
  (предупреждение MSB8029), а трекер файлов MSBuild временный каталог не
  отслеживает — правка заголовка НЕ пересобирает зависящие .cpp (12.09: новый
  параметр `RemovePlayer` → LNK2019 в нетронутых session_hooks.obj и
  packet_handler.obj). Смена раскладки структуры в заголовке прошла бы молча, со
  старыми смещениями полей. Команда:
  `cmake --build build --config Release --target ds2_seamless_coop --clean-first`.
- **С 12.09 (версия 0.1.0) проект живёт в репозитории**
  [Restezzz/Seamless-DarkSouls2](https://github.com/Restezzz/Seamless-DarkSouls2):

## 10. Открытое

- Мировые предметы в чужом мире — сделано (раздел 3.3), ждёт проверки в игре.
  Дальше по той же схеме: **сундуки** (`0x1CF930` — тот же гейт `0x1E26F0`, но у
  сундука ещё состояние крышки в записи объекта) и дроп с мобов (`0x1E2580`: в
  мультиплеере берёт другой лот, `[row+0x138]` вместо `+0x88`).
- **Поле `+0x1374` (значение 513)** первого из объектов `[GMImp+0x38]`,
  `[GMImp+0x10]`, `[[GMImp+0x10]+0x18]`: старый «TeamType»-скан во всех сессиях
  на обеих машинах попадал именно в него (и у хоста в своём мире — значит, не
  TeamType) и обнулял. Скан убрали — в той же сессии автопризыв хоста не
  отправил `RequestSummonSign`. Вернули точечно (только это поле, только 513–516).
  Что это за поле — не выяснено; прямых обращений с этим смещением в коде нет
  (`Grep` нашёл одну чужую инструкцию). Нужна проверка вкл/выкл.
- Долгая сессия у хоста: области, выгруженные в мультиплеере, не пишут своё
  состояние (`0x1F3A80`) — подбор хоста спасает `ds2_coop_loot.txt`, двери/рычаги
  держатся на флагах событий.
- Общий прогресс включён по умолчанию (`flag_sync=on`, §3.21): костры, туманы, боссы и
  предметы идут диффом в обе стороны, а хост при входе гостя отдаёт всё уже сделанное.
  Пишет в сейв получателя; таблица флагов сама сохраняется в `ds2_flags_backup.bin`.
- Смерть хоста: блокировка разрыва даёт «зомби-сессию».
- Мелок в запретных зонах остаётся серым (обход — установка знака модом).
- Состояние врагов между игроками — через `EnemyGeneratorPacketCtrl` (раздел 3.2).
